Level 1: The order of events

Ожидаемый порядок: A, B, C, 6 students (если бы код был синхронным).
Порядок на выходе: A, C, (первый фрейм приложения), fetchStudents #1, B, 6 students.
Вывод: Синхронный код (A и C) выполнился сразу, а асинхронный (B и данные студентов) ушел в Event Loop и вернул результат только через 2 секунды, не блокируя отрисовку UI.

При вызове fetchStudents() три раза подряд, на третий раз выбрасывается Unhandled Exception: Instance of 'NoConnectionException'. Приложение не ломается и продолжает работать.

Level 2: setState called after dispose

Эксперимент: Если закомментировать `if (!mounted) return;` в методе `_load()` и закрыть экран во время ожидания данных.
Результат: Выбрасывается ошибка `FlutterError (setState() called after dispose(): _StudentsScreenState#...)`.
Вывод: Асинхронный метод `fetchStudents()` продолжает работу в фоне. Когда он завершается, он пытается обновить UI через `setState()`, но экран уже уничтожен (`dispose`). Проверка `mounted` спасает приложение от краша.

Level 3: FutureBuilder
*Эксперимент: Переключение Switch на экране FutureBuilder.
Результат: Новые логи `fetchStudents` в консоли не появляются.
Вывод: Так как вызов API сохранен в переменную `_future` внутри `initState`, запрос уходит только один раз. Вызов `setState` при переключении свитча перестраивает только UI-интерфейс, не отправляя повторных сетевых запросов.

Level 4: A countdown that stops
Эксперимент: Если закомментировать `_sub.cancel()` в методе `dispose()` и выйти с экрана Countdown во время работы таймера.
Результат: Консоль продолжает непрерывно печатать `tick 7`, `tick 6`, `tick 5`... даже после закрытия экрана.
Вывод: Поток продолжает жить в памяти (утечка памяти / memory leak). Метод `_sub.cancel()` в `dispose()` жизненно необходим, чтобы вовремя уничтожать подписку при закрытии виджета.

Level 5: Errors that do not vanish
Логика: При сохранении данных на сервер используется блокировка кнопки (`_saving`), чтобы избежать повторных запросов. Ошибки сервера перехватываются локально через `try/catch`, выводятся пользователю через `SnackBar`, но экран не закрывается принудительно, предотвращая ложное ощущение успешного сохранения.
